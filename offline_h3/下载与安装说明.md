# H3 本地下载与服务器离线安装

更新：2026-10-30。用户已向平台确认依赖需要自行配置，因此现在按个人 AFS 内的虚拟环境和离线安装准备；前一份流程复核中“先等待管理员发布环境”的建议已被这一确认替代。

本目录提供的是清单和下载工具，不是已经下载好的依赖包。助手执行环境目前无法解析 PyPI、GitHub、厂商索引域名，未在线核实包是否仍可下载，也未运行远端安装。版本来自所提供 POD 指南；下载工具遇到缺失版本或依赖冲突会停止，不自动换版本。

## 1. 全部资源清单

目标为 Linux x86_64、CPython 3.11、厂商 PyTorch 2.9.0+das.opt1.dtk2604、DTK 26.04、gfx936、C++11 ABI=1。不要下载 Windows wheel、普通 NVIDIA FlashAttention，或替换系统 torch。

### 非 pip 构建依赖

| 资源 | 当前证据 | 下载或准备要求 |
| --- | --- | --- |
| xmake | 服务器 PATH 未找到；Slurm 指南验证 3.1.2 | https://github.com/xmake-io/xmake/releases/tag/v3.1.2 。工具可拉取该 tag 及其子模块源码；目标需要 gcc/g++、make 等构建条件，或使用匹配 Linux x86_64 的便携发行包 |
| Boost（启用 stacktrace） | InfiniCore/xmake.lua 的 add_requires | 通过固定的 xmake-repo 配方解析，准备源码缓存或匹配系统的导出包 |
| pybind11（xmake 包） | InfiniCore 和 InfiniLM 均 add_requires | 必须准备 xmake 所需的包，不能只拿 pip wheel 当作已满足 |
| OpenMP（xmake 包/系统开发库） | 默认 omp=y，cpu.lua 显式 add_requires | 即使主要运行 DCU，默认构建仍包含 CPU 部分；需系统可用或离线包 |
| xmake-repo 配方及其传递构建工具 | xmake 默认在线获取 | 和上述包缓存一起准备；只有 xmake 可执行文件不能保证离线配置成功 |
| InfiniCore/InfiniLM 源码及使用到的子模块 | 已有官方基线与用户修改 | 保留用户当前 InfiniLM 改动；检查 spdlog/include、json/single_include 等实际存在，空 gitlink 不能替代文件 |
| libflash_attention.so | 当前 InfiniCore 海光 flash-attn 构建会链接 | 需要与基线及 DTK/torch ABI 匹配的库/构建产物，放在所配置 flash-attn 根目录的 flash_attn/lib 下；不能假设厂商 Python wheel 一定提供 |
| DTK 兼容 CUDA 头文件及库 | 已有编译器，但库尚未全面实测 | 复用 /opt/dtk；构建使用 cudart、cublas、cublasLt、curand、cudnn，以及通信 nccl 兼容接口。缺失时取得 DTK 匹配组件，不安装公共 NVIDIA CUDA/NCCL wheel 替代 |
| Python 3.11 开发头文件、make、链接器、libstdc++ | 原生构建必需 | 由目标系统提供，缺失时取得兼容开发组件；cmake/ninja 已确认存在，无需重新上传 |

**原生依赖不能仅靠 requirements.txt 完成。** 当前源码没有固定 Boost/pybind11/OpenMP 配方版本，文档也没有提供预制离线缓存。因此这里没有编造一个“下载几个压缩包即可完全离线编译”的承诺。

推荐在联网、尽量匹配服务器发行版/GCC 的 Linux 准备机上使用 xmake 3.1.2：用一个小型准备工程声明与当前源码相同的 `add_requires("boost", {configs={stacktrace=true}})`、`add_requires("pybind11")`、`add_requires("openmp")`，完成包解析；按该版本 `xmake require --help` 的导出功能导出包，并保留所用 xmake-repo 提交与下载缓存。在目标导入后验证当前源码的离线 `xmake f`。仅复制普通 pip 缓存或 xmake 可执行文件都不足以替代这一步。若准备机 ABI 不匹配，应准备源码缓存在目标构建，不能直接复用准备机生成的库。

已经提供上述准备工程 `native-package-project/`。本地安装 xmake 3.1.2 后，在这个目录执行：

```bash
xmake f -y -c -m release
xmake build -j4
xmake require --help
```

这会实际解析并下载原生包及其传递构建资源。若该版本帮助中提供 `--export`，可执行 `xmake require --export=/绝对路径/h3-native-packages`，目标端使用对应 `--import` 导入；路径及选项以该版本帮助为准。还需携带使用的 xmake-repo 配方和下载缓存，以便目标配置查找同一版本。小工程通过只验证准备机的包，不证明目标 DTK 的链接与 ABI 通过；当前助手没有 xmake，未执行这一原生准备步骤。

## 2. 在本地联网电脑下载

使用 **Linux x86_64 或 Windows WSL 内的 Python 3.11**。Windows 原生 Python、macOS 不直接运行本工具，以免依赖环境标记与目标 Linux 不一致。本地不需要 GPU，也不会运行模型。

将整个 `offline_h3` 工具目录放在本地。在其中运行：

```bash
python3.11 -m venv .download-env
source .download-env/bin/activate
python -m pip install --upgrade pip setuptools wheel packaging
```

如果第一步报 `ensurepip` 失败，后续激活命令不要继续执行。当前本地 Ubuntu 的 `/usr/bin/python3.11` 缺少 ensurepip，但系统提供 `/usr/share/python-wheels/pip-22.0.2-py3-none-any.whl`，可在创建 `.download-env` 的同一目录离线补全环境：

```bash
/usr/bin/python3.11 -m venv --without-pip .download-env
.download-env/bin/python - <<'PY'
import runpy, sys
from pathlib import Path
wheel = Path('/usr/share/python-wheels/pip-22.0.2-py3-none-any.whl')
assert wheel.is_file(), '本机无此 pip wheel；需取得可用 pip wheel 或安装匹配的 python3.11-venv'
sys.path.insert(0, str(wheel))
sys.argv = ['pip', 'install', '--no-index', '--no-deps', '--no-cache-dir',
            '--ignore-installed', '--disable-pip-version-check', str(wheel)]
runpy.run_module('pip', run_name='__main__')
PY
source .download-env/bin/activate
python -m pip --version
python -m pip install --upgrade pip setuptools wheel packaging
```

这里固定的路径来自当前本地 Ubuntu 检查，不适用于所有机器或比赛服务器。离线 wheel 用于恢复 pip；最后的升级仍需联网。`python` 命令由成功激活的环境提供，不需要为此单独安装 `python-is-python3`。

先下载普通包，之后即使厂商站点不可达也已经拿到这一部分：

```bash
python download.py --stage public --out public-download
```

单独下载精确厂商 wheel：

```bash
python download.py --stage vendor --out vendor-download
```

准备完整 Python 依赖闭包、torchvision/xmake 源码，优先使用已经取得的官方 Diffusers 源码目录：

```bash
python download.py --stage complete --native-sources \
  --diffusers-source /实际路径/官方验证的diffusers \
  --out complete-download
```

如果暂时只有文档里的候选分支，可改用：

```bash
python download.py --stage complete --native-sources \
  --diffusers-ref minimax-h3 \
  --out candidate-download
```

此时成功只说明包和基本 H3 目录存在，不代表等于官方版本。服务器还需验证 `MiniMaxH3Transformer3DModel`、`ModularPipeline`、H3 模块、`encode_video` 的导入与实际行为。要把 NineToothed/ntops 也纳入解析，给 complete 命令加 `--include-nine`，使用另一个输出目录。

三个阶段是可独立运行的方案；**只运行 complete 成功时，不必再运行 public/vendor**。阶段下载重复的包不会带来必要性，已有阶段目录主要用于排查哪个来源失败。脚本会拒绝混入已有的 upload 输出目录。

下载工具使用一个真实的 **CPU torch 2.9.0 wheel，仅在本地解析依赖**，避免普通 torch 拉入数 GB 的 NVIDIA 库。该文件不会进入 `upload-*`，也不会在服务器安装。厂商 torch 的特有依赖仍以目标镜像为准；如果厂商插件严格要求带厂商后缀的 torch 元数据，pip 会报冲突，此时应保留错误并按其真实依赖补齐，不得强行把 CPU torch 安装到服务器。

工具默认选择 glibc 不高于 2.28 的 manylinux wheel，另允许厂商使用的 linux_x86_64 标签。服务器实际 glibc 可用 `python -c 'import os; print(os.confstr("CS_GNU_LIBC_VERSION"))'` 查看；若更低，设置 `--glibc-minor`。`linux_x86_64` 标签本身不保证 glibc 兼容，厂商库仍需要实测。

## 3. 上传和空间

只上传完成目录 `*-download/upload-*`，其中应有 `READY.txt`、`manifest.json`、`SHA256SUMS`，且没有 `INCOMPLETE.txt`。`local-only` 不上传，里面包含本地解析用的 CPU torch 及工作文件。

普通和 complete 阶段还会生成带 SHA256 的 `install.lock`。vendor 阶段只有厂商包，没有传递依赖闭包，不能单独当作完整安装目录。

完整包应放在个人 AFS，而不是有项目复制上限的“我的项目”。网页单文件 128 MiB 上限可通过分块处理，例如对一个超过限制的 wheel：

```bash
# 本地；对实际文件名操作。不要把 .part 文件交给 pip。
split -b 120M large-package.whl large-package.whl.part-
# 服务器 AFS 同目录中；确保所有分块都上传完成。
cat large-package.whl.part-* > large-package.whl
```

重组后，回到 upload 目录运行 `sha256sum -c SHA256SUMS`。校验成功后再手动清理自己的分块以释放空间。这个方法需要分块与重组文件短时同时存在，应先核算空间；也可在平台允许的临时盘重组。

原 FlashAttention .so 已知约 1.95 GiB。4 GiB AFS **不能预先保证**足够容纳所有压缩包、安装结果、Triton、torchvision/native 编译中间文件和输出。下载工具输出 wheel 压缩与展开大小，但不包含全部编译峰值。若预算超出，应分批上传/安装/清理已验证的安装介质，使用允许的临时构建空间或扩容。

## 4. 服务器安装 Python 包

完成目录可执行：

```bash
cd "$IFAB_AFS_HOME/实际上传目录/upload-complete"
bash install_python.sh
```

这会创建 `$IFAB_AFS_HOME/envs/h3` 的 `--system-site-packages` 虚拟环境，保留厂商 torch，使用离线锁文件安装全部准备好的 wheel，禁止 pip 再联网或递归安装其他包。也可使用 `H3_VENV` 指定另一个个人目录。

public 阶段同样可以安装，但仍缺 Diffusers/厂商包。不要只运行 public 后就尝试全模型。若 venv/ensurepip 自身不可用，需要另行准备虚拟环境工具；目前用户尚未报告这一问题。

之后构建 torchvision（源码包先解压到自己的 AFS 或允许的临时构建目录）：

```bash
source /opt/dtk/env.sh
source "$IFAB_AFS_HOME/envs/h3/bin/activate"
cd /实际解压目录/torchvision-v0.24.0
export BUILD_VERSION=0.24.0
export FORCE_CUDA=1
export MAX_JOBS=4
export PIP_NO_INDEX=1
python -m pip install . --no-deps --no-build-isolation --no-cache-dir
```

MAX_JOBS=4 是减少构建峰值的起点，可按平台资源调整。官方指南采用 16。离开源码目录后验证 torchvision transforms 与 nms 注册；再按官方基线构建 InfiniCore/InfiniLM，统一 `HYGON_ARCH=gfx936`、`INFINILM_CXX11_ABI=1`，配置实际的 `INFINI_ROOT` 和库目录。当前 InfiniLM 没有旧 `infinicore_infer` target。

厂商插件安装到个人环境后，选择**个人 venv 中**的可读文件：

```bash
source "$IFAB_AFS_HOME/envs/h3/bin/activate"
export FA_SO_PATH="$(find "$VIRTUAL_ENV/lib/python3.11/site-packages" -maxdepth 1 -name 'flash_attn_2_cuda*.so' -print -quit)"
test -n "$FA_SO_PATH"
export FLASH_ATTN_2_CUDA_SO="$FA_SO_PATH"
```

前者供海光 PyTorch SDPA 使用，后者供 InfiniCore 原生构建使用。实际读取和加载仍需验证；不再使用此前被拒绝访问的系统文件作为已满足依赖的证据。

`imageio-ffmpeg` 包含自己的 ffmpeg 可执行文件，但不一定自动出现在 PATH。若具体调用使用命令名 `ffmpeg`，应使用 `imageio_ffmpeg.get_ffmpeg_exe()` 获取实际路径，并在个人 bin 目录建立链接或配置对应环境变量。PyAV 的编解码不等同于系统已有 ffmpeg 命令。

最终依次验证 `python -m pip check`、H3/torchvision 导入、强制 Flash SDPA 的小张量运算、InfiniCore/InfiniLM 原生导入，再进行 --legacy 和原生 FL2VA 冒烟。pip check 可能报告继承系统环境的其他包冲突，需区分 H3 依赖冲突；不能把导入成功等同于 ABI 与运行正确。

## 5. 尚未由现有材料确定的事项

- 官方验证的 Diffusers 精确 commit/软件包，dev 版本号不足以唯一确定。
- xmake 实际选用的包配方版本与离线缓存闭包。
- 原生 InfiniCore 所需的匹配 libflash_attention.so 是否包含在可取得的厂商交付中。
- NineToothed/ntops 与 gfx936 厂商后端的验证版本。
- 目标 glibc、实际可写构建峰值空间及安装后个人库的加载权限。

这些事项会影响“完整可运行”的判断，但不妨碍先下载已明确的普通依赖与厂商 wheel。清单已覆盖当前代码、模型 requirements 和 POD 指南中能够识别的依赖；未取得实际包前，不把它标记为通过远端验证的离线发布包。
